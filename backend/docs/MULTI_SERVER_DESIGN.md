# 工作室多域名、多服务器与超管汇总

日期：2026-09-28。状态：**设计方案，尚未接入运行代码**。

## 1. 先区分已实现与待实现

- 已实现：本机 Vue + Node、单 SQLite、超管登录、一个账号一个固定 APK ID、构建时解析实际编号、独立设备登记凭证、无障碍首图与网页租约内实时最新帧。
- 当前 `config.projectId` 仍固定为 1；`backendOrigin()` 只检查地址格式并写入 APK；`android/apk-templates/domains.json` 当前为空。填写一个域名不等于已经开通工作室、部署节点或同步到超管。
- 当前超管查看的是当前服务数据库中的全部项目，不是自动发现其他服务器的设备。
- 总台/子账号、受验证的域名绑定、节点身份、中央同步、跨节点预览、节点到期联动均待实施。本次不改运行模式、不开放监听、不创建远端服务器。

## 2. 推荐架构：中央管理服务 + 工作室接入节点

```text
工作室 A 的 APK ─HTTPS/WSS→ A 域名 → A 接入节点 ─受限服务 API→ 中央 Node
工作室 B 的 APK ─HTTPS/WSS→ B 域名 → B 接入节点 ─受限服务 API→ 中央 Node
                                                               │
                                                     账号 / 归属 / 期限 / 审计
                                                               │
                                                           中央 SQLite
                                                               ↑
                                                  超管后台统一查询与订阅
```

- **中央管理服务**拥有账号、全局唯一 APK ID、工作室、有效期、域名/节点映射、设备归属、构建记录和审计的权威数据。
- **工作室接入节点**运行在独立服务器，承接本工作室手机连接、状态和临时截图；调用中央业务 API，不直接连接或拷贝中央数据库，不持有超管会话或中央主密钥。
- **工作室后台**可部署相同 Vue 前端，管理请求由其 Node 服务携带节点身份及用户授权交给中央处理。页面不自行决定租户范围。
- 这里的“独立服务器”是接入、带宽与运行资源独立，不是脱离中央的离线独立产品。中央可用性仍是依赖；需要完全离线运营时应另做冲突/授权设计。
- 使用同一代码仓库，逐步增加中央/节点运行职责；此阶段不拆微服务仓库，不引入消息中间件或全量数据库双向同步。

## 3. APK ID、域名、设备归属的关系

| 标识 | 含义 | 谁决定 |
|---|---|---|
| APK ID | 一个账号的固定业务编号，全平台唯一 | 中央在创建账号的事务中分配 |
| 工作室域名 | 手机连接的接入地址 | 超管登记、验证并绑定工作室/节点 |
| studio_id / project_id | 服务端内部工作室范围，不是业务 AppID | 中央认证与租户关系 |
| node_id | 一台接入节点的身份 | 中央登记节点后分配 |
| device_id | 中央登记后的设备标识 | 中央登记事务 |
| owner_account_id | 设备当前分配给谁 | 中央归属记录；允许后续有审计的内部下发 |

示例仅用于解释关系：

| 构建者 / 选择 | 连接域名 | APK 内实际编号 | 首次归属 |
|---|---|---|---|
| A 总台，自己的编号 10074 | a.example.com | 10074 | A 总台 |
| A 子账号，自己的编号 10075 | a.example.com | 10075 | A 子账号 |
| A 工作室构建，编号留空或未匹配可用账号 | a.example.com | 10074 | A 总台 |
| B 总台，自己的编号 20074 | b.example.com | 20074 | B 总台 |

**域名区分工作室入口，APK ID 区分工作室内接收账号；超管是否可见由中央访问权限决定，而不是 APK 再填一个超管编号。** 一个账号的编号保持固定；一个工作室后续可绑定多个经过验证的域名。

### 构建阶段

1. 中央根据登录会话确定工作室。总台/子账号只能选择本工作室已验证、已启用的域名，通常自动填入默认域名；超管先选目标工作室，再选择该工作室的域名。公网版本不沿用当前任意填写 HTTPS 地址的规则。
2. APK ID 匹配限所选工作室内的启用、未到期账号；留空、未知、不可用或其他工作室的编号均不命中，统一采用本工作室总台编号，并在回执显示实际接收方。没有可用默认接收账号则报错，不回落到其他工作室或平台超管。
3. 未知/停用域名、域名与所选工作室不一致、工作室到期、节点未就绪属于配置错误，停止构建；不把域名错误当作编号为空处理。
4. 入队事务保存工作室、域名、实际 APK ID、接收账号和配置版本快照，构建 UUID 幂等。APK 仍只写工作室入口、实际编号等公开配置，不打入节点凭证、账号 Token 或通用登记密钥。
5. 构建可以先继续由中央现有串行 Worker 执行。工作室机器人只是受限的提交入口，依然通过中央鉴权/配额/队列，不必给每台接入节点安装 Gradle。

### 首次上线阶段

1. 手机连接工作室域名，提交独立登记凭证、APK ID 和原有基础设备字段。
2. 节点身份绑定 `node_id + studio_id`；中央核对节点、登记许可、域名配置与 APK ID 的租户关系，实际 owner 从中央记录取值，不采用手机提交的 owner/project 字段。
3. 中央先完成登记事务、固定归属并生成设备身份，节点再向手机返回成功。客户端安装标识只作为本工作室内的重试关联，不被当作跨工作室所有权凭据。
4. 上线请求中的未知/被篡改编号或租户冲突直接报错。**“编号留空/填错回总台”仅发生在可信构建阶段**，已将正确编号写进 APK；不是让任意手机绕过登记或改变归属。
5. 已登记设备重连按设备凭证读取中央已有归属，不重新按 APK ID 分配；后续在后台下发给子账号后，旧 APK 的编号不会把它抢回总台。

## 4. 超管怎样看到独立服务器的设备

### 设备列表与状态

- 首次登记本来就写入中央，所以中央有全平台设备索引。每条保留工作室、当前 owner、接入 node、最后状态时间与归属版本。
- 节点向中央发送本节点已登记设备的白名单状态；中央核对设备确实属于该节点及工作室，再更新并向已授权的网页 WS 订阅者广播。设备状态是节点报告，不伪装成中央独立验证。
- 超管查询全部工作室；总台查询本工作室；子账号查询本工作室中分配给自己的设备。相同范围校验覆盖详情、图片、导出、统计、构建产物和 WS，而不只是列表。
- 心跳先合并更新内存状态，按有界频率持久化最后在线时间；不把每次心跳或画面都写进 SQLite。
- 中央显示节点是否连通和状态时间。节点失联标注“节点失联 / 状态未知”，不继续显示所有设备实时在线，也不把失联直接解释成手机关机。

### 查看手机已确认上传的单张截图

- 图片留在工作室节点的有界临时内存，沿用当前 5 分钟过期、停止/撤销清理规则；中央只记录有界的临时帧索引，不永久复制或归档图片。
- 超管点击查看 → 中央检查登录态、角色、有效期和设备范围 → 向该设备已登记节点请求特定未过期图片 → 经中央受控响应返回浏览器。
- 节点再次校验限定用途、设备、帧、节点及短有效期的查看凭据，并检查当前归属/撤销状态。输出 no-store，不生成公共图片地址。
- 中央只访问运维登记的节点地址，忽略客户端传入的任意上游 URL；限制响应大小、超时并禁止重定向到其他目标。
- 因此 APK 不用向超管和工作室重复上传；只有查看图片时才需要节点到中央的受控传输。节点不在线或图片过期时展示具体状态，不展示旧图为新图。
- 本设计沿用手机主动确认的一次上传，不添加网页发起采集、连续采集或手机操作能力。

## 5. 节点认证、中央会话与故障处理

- 每个节点独立服务身份和最小工作室范围，建议使用 mTLS 与成熟 TLS/认证库；凭证独立轮换/撤销，不跨工作室复用。节点只持自己的身份材料，不持中央数据库密码、超管 Token 或中央 `master.key`。
- 中央统一账号认证、续期与单端会话；域名下 Cookie 不互相拷贝。跨域登录使用成熟的标准身份流程，节点受众与工作室范围必须验证，普通账号不取得全局身份。
- 公网多节点阶段采用中央签发、节点验证的独立设备凭证或在线核验；不把当前本机 HS256 主密钥复制到所有服务器。选型和密钥轮换需要单独实现/验收。
- 第一版需要新授权的操作，包括账号登录、设备登记、归属变更和图片上传/查看许可，均以中央核验成功为准。节点保留中央已确认状态的只读缓存，不在断联时自行开通账号、延长有效期或重分配设备。
- 节点到中央失联时结束单次上传许可与敏感查看，页面显示不可用；元数据队列有大小与时间上限。恢复时带事件 ID/设备版本幂等同步，旧状态不覆盖更新的中央归属，临时图片不为重试而长期落盘。
- 工作室到期、账号停用、节点撤销时停止新登记和管理访问，失效通知清理相关订阅/临时图片，重连仍重新检查；账号/历史归属不删除。超管保留合同和历史记录管理，但不因全局角色绕过手机共享确认。
- 管理、构建、节点同步、取图分别限流和审计；日志只保留主体/对象标识、事件类型、时间与结果，不保存图片、凭证、密码或短信正文。

## 6. SQLite 与数据模型

当前仍使用 SQLite：**只有中央 Node 访问中央本地 SQLite 文件，其他服务器调用业务 API**。不通过 NFS/共享磁盘让多机直接操作同一文件，不向工作室分发整库副本。节点可有独立的有界元数据重试队列，它不是账号或设备归属的权威数据库。

业务增长到中央需要多实例并发写入/高可用时，再评估 PostgreSQL/MySQL 迁移；独立接入节点不等于现在必须换库。节点减少连接与图片处理负担，但不会自动解决中央 API/SQLite 的吞吐瓶颈，需容量测试。

建议后续增量模型（本轮未建表）：

| 数据 | 最小关系 |
|---|---|
| studios | 总台账号、默认接收账号、期限、启用状态 |
| accounts | 中央唯一 APK ID、角色、所属工作室、上级账号 |
| studio_domains | 已验证域名、工作室、当前节点、启用状态 |
| server_nodes | 工作室、节点身份引用、受控接入地址、心跳与状态 |
| devices | 中央设备 ID、工作室、当前 owner、当前 node、归属版本 |
| apk_builds | 工作室、构建时域名/编号/归属/配置版本快照 |

已有 `project_id` 必须明确映射到工作室租户；不要另加一套相互矛盾的 `studio_id` 过滤。所有业务表、文件索引、缓存键与 WS 订阅带相同服务端确定的租户上下文。APK ID 从中央统一分配，独立节点不使用自己的自增号分配账号编号。

## 7. 域名、迁移与交付顺序

1. 先做中央总台/子账号、唯一编号、5 个子账号限额、期限继承和全链路租户隔离；通过两个工作室的互访否定测试。
2. 再做域名/节点登记，工作室域名改为受控选择；先允许多个域名绑定同一个节点，验证 APK ID 与工作室关系。
3. 增加独立节点认证、登记转发、状态汇总及超管查询；用两个隔离测试节点验证到期、断联、重放、乱序、撤销和跨节点冲突。
4. 最后接受控图片预览、工作室机器人构建入口，做带宽/内存/队列上限及公网部署验收。没有任务要求时不自动部署公网。
5. 更换服务器时优先保留工作室域名及 HTTPS 入口，协调凭证受众、在途连接与节点迁移版本，使旧 APK 重连后使用已有中央归属。更换域名则旧 APK 仍带旧地址，需保留原入口过渡或重新构建安装，不声称数据库改域名会自动更新已安装 APK。

## 参考依据

- [SQLite 官方适用场景](https://www.sqlite.org/whentouse.html)：SQLite 可作为单个应用服务后的本地数据库；避免多台计算机通过网络文件系统直接并发读写同一数据库文件。
- [OWASP 多租户隔离指南](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)：客户端租户标识只是选择条件，业务范围应绑定到已核验身份；检查须覆盖数据、缓存、异步任务与文件访问。
