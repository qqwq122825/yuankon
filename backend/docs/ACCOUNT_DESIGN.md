# 账号与归属设计 · 2026-09-28

## 本轮已实现：只有超管

当前账号角色仍只有超级管理员，不创建总台或子账号。后续增量已实现 APK ID 首次归属与 ScreenAgent 单张截图接入，详见 [接入契约](SCREENAGENT_INGRESS.md)；下文账号层级与自动下发仍是规划。

- Vue + Node 同域运行，SQLite 位于 `backend/.node-private/boundary.sqlite`。旧 PHP 运行数据已移出项目私有备份，不参与当前运行。
- 首次启动初始化超管 `mtx` / `mtx123`，密码以 Argon2id 散列保存。重启不重置密码，不重复创建账号。
- 打开 [登录页](http://127.0.0.1:8080/login)，登录后右上角「账号设置」支持退出与修改密码。
- 使用 Passport Local/JWT 与 jose。HTTP Token 有效期 8 小时；浏览器使用 HttpOnly、SameSite=Strict、Path=/api 的 Cookie，不将 Token 放入 localStorage。Bearer Token 可用于本机 API 调试，两者同时存在时以 Authorization 为准。
- 每个账号在 SQLite 只保留一个有效 `session_id`。新登录替换旧会话；旧 Token/图片/导出/API 请求立即失效，已有面板 WS 收到会话结束通知，旧页面返回登录。
- 同一浏览器共享 Cookie 的标签页属于同一次登录；「单端」指单个有效登录会话，不是只能打开一个标签页。IP 不作为设备身份。
- 退出、改密撤销当前会话，WS 也断开。账号停用或角色变化会在每次 HTTP、WS 业务消息及广播时重新检查。
- 管理端业务 API 均需登录；设备专用登记/上报路由分别校验短效登记码和设备 Token。面板 WS 使用从登录态换取的 10 分钟专用票据，与 HTTP Token 和设备凭证相互隔离。
- 登录失败与改密校验采用限流；账号审计仅保存事件、操作者 ID、IP 和时间，不保存密码、验证码、Token 或请求正文。
- 超管跨所有 `project_id` 查看设备、历史记录和现有管理功能。设备与快照的关联完整性、图片路径检查、正文剔除仍然保留。
- 已有管理功能包含列表、备注、查看、导出及新设备登记/单张截图；没有新增手机操作指令或连续采集。

服务仍仅绑定 127.0.0.1，并保留 Host、Origin、转发头与同源 JSON 写请求检查。默认密码仅用于本机初始化；对外部署前更换密码、启用 HTTPS/WSS、完善租户隔离与访问审计，另做部署验收。当前并非公网成品。

## 后续方案：未实施

### 1. 账号层级

| 角色 | 建议范围 |
|---|---|
| 超管 | 全部工作室、全部设备、创建总台、归属调整及审计 |
| 总台 | 自己的工作室设备与配置；创建最多 5 个有效子账号；工作室内部下发设备 |
| 子账号 | 仅被分配给自己的设备及允许的功能 |

总台对应工作室租户，服务端内部使用 `studio_id` / `project_id` 做隔离。这些是内部归属主键，**不叫 AppID，也没有「总台 AppID」这一业务字段**。本轮没有提前加入租户表、创建账户路由或虚假的管理按钮。

后续实现时，所有查询、图片/导出、WS 订阅和广播必须统一校验角色与归属，不能只隐藏前端列表。5 个子账号的限额在数据库事务中检查，避免并发创建超额；父账号停用时一并撤销相关会话。

### 2. 只有 APK ID：区分构建、路由与凭证

- `APK ID`：构建配置的业务标识，例如 `10074`。关联接入域名、工作室、默认接收账户或待分配池。
- `构建 ID`：一次具体构建任务的标识，例如 `5412ce7f`，与 APK ID 分开。一次 APK 配置可有多个构建版本。
- 域名：负责连接到哪个服务入口；APK ID 负责查默认归属。域名不是用户账号，也不是权限凭证。
- 用户专属 APK 默认进入该用户的设备列表；总台 APK 先进入该总台待分配池；超管 APK 可进入平台待分配池，再经后台操作指定工作室与用户。
- 设备首次登记后，实际归属保存在服务端。后续下发更新服务端归属和审计，重新计算可见性/订阅并撤销旧权限；设备重新连接不得覆盖已生效的分配结果。
- APK ID 可公开，不能单独凭它信任数据或访问其他设备；每台设备仍需独立登记凭证，服务端校验设备与项目关系。

当前接入副本已经使用 APK ID 查后台默认归属，并保存设备实际 owner_account_id；目前只配置到超管。未实现总台/子账号、归属下发、旧设备恢复或多域名部署；原浏览器模板保持不变。

### 3. 专属域名、专属服务器与中央数据库

建议先用单 Node 服务与 SQLite 验证账号逻辑，再逐步拆分部署，而非现在启动微服务：

1. 一个工作室绑定一个经过验证的域名；服务端维护域名到工作室的映射，拒绝未知 Host。域名映射不替代账号权限校验。
2. 初期多个域名可指向同一服务与数据库；总台只访问自己的租户数据，超管保留全局视图。
3. 需要专属服务器时，中央服务保留账号、归属、构建配置和审计的权威数据。专属节点以工作室限定的服务凭证调用中央 API，断联时停止需要新权限确认的操作，不擅自扩大权限。
4. 不让多台服务器经共享磁盘直接读写同一 SQLite 文件；达到多节点/写入量需求后，迁移至集中 PostgreSQL/MySQL，或者继续由中央单服务独占 SQLite 并通过 API 访问。该数据库迁移尚未实现。

按「平台统一持有数据库、总台管理自己工作室数据」理解当前意图；若以后每个总台独立持库，需另定平台汇总和数据同步边界。

### 4. 总台机器人验证码

后续每个总台配置自己的机器人 Token（加密存储），用户经一次性短效绑定链接绑定 Telegram 私聊身份，不仅凭用户名绑定。登录流程建议：

1. 账号密码验证成功，生成短效登录挑战，此时还不签发账号 Token。
2. 为该挑战生成 6 位随机验证码，通过所属总台机器人发送给已绑定的私聊；显示用户、服务端获取的 IP 和 5 分钟有效期。
3. 只保存带服务端密钥的验证码校验值，绑定账号和挑战；一次使用、限次验证、限速发送。重发撤销旧验证码，成功或到期删除挑战。
4. 验证成功后再创建唯一会话并挤下旧登录；不让仅输入正确密码的人提前挤下正在使用的账号。
5. 机器人失联、未绑定、重绑定与丢失账号的人工处理流程需单独设计；错误和日志不记录验证码正文。平台超管的机器人归属也在这一阶段单独配置。

以上均为规划。当前账号密码可直接登录，机器人验证码尚未启用。
