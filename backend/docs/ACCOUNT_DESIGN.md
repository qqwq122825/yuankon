# 账号与归属设计 · 2026-09-28

## 本轮已实现：只有超管

当前账号角色仍只有超级管理员，不创建总台或子账号。后续增量已实现 APK ID 首次归属与 ScreenAgent 实时最新帧接入，详见 [接入契约](SCREENAGENT_INGRESS.md)；下文账号层级与自动下发仍是规划。

- Vue + Node 同域运行，SQLite 位于 `backend/.node-private/boundary.sqlite`。旧 PHP 运行数据已移出项目私有备份，不参与当前运行。
- 全新数据库首次访问 `/install` 设置唯一初始超管账号和任意非空密码；密码与确认密码可同时切换显示。服务端事务创建账号、固定 APK ID `1` 与审计记录，密码以 Argon2id 散列保存。成功后生成私有完成锁并永久关闭账号初始化；登录账号仍可在 `/install` 检测或补齐构建环境。重启不重置密码，不重复创建账号。已有超管的旧实例升级时自动补写完成锁。
- 打开 [登录页](http://127.0.0.1:8080/login)，登录后右上角「账号设置」支持退出与修改密码。
- 使用 Passport Local/JWT 与 jose。HTTP Token 有效期 8 小时；浏览器使用 HttpOnly、SameSite=Strict、Path=/api 的 Cookie，不将 Token 放入 localStorage。Bearer Token 可用于本机 API 调试，两者同时存在时以 Authorization 为准。
- 每个账号在 SQLite 只保留一个有效 `session_id`。新登录替换旧会话；旧 Token/图片/导出/API 请求立即失效，已有面板 WS 收到会话结束通知，旧页面返回登录。
- 同一浏览器共享 Cookie 的标签页属于同一次登录；「单端」指单个有效登录会话，不是只能打开一个标签页。IP 不作为设备身份。
- 退出、改密撤销当前会话，WS 也断开。账号停用或角色变化会在每次 HTTP、WS 业务消息及广播时重新检查。
- 管理端业务 API 均需登录；设备专用登记/上报路由分别校验短效登记码和设备 Token。面板 WS 使用从登录态换取的 10 分钟专用票据，与 HTTP Token 和设备凭证相互隔离。
- 登录失败与改密校验采用限流；账号审计仅保存事件、操作者 ID、IP 和时间，不保存密码、验证码、Token 或请求正文。
- 超管跨所有 `project_id` 查看设备、历史记录和现有管理功能。设备与快照的关联完整性、图片路径检查、正文剔除仍然保留。
- 已有管理功能包含列表、备注、查看、导出、新设备登记及查看租约内的实时最新帧；没有输入控制或完整诊断会话。

服务仍仅绑定 127.0.0.1，并保留 Host、Origin、转发头与同源 JSON 写请求检查。默认密码仅用于本机初始化；对外部署前更换密码、启用 HTTPS/WSS、完善租户隔离与访问审计，另做部署验收。当前并非公网成品。

## 账号卡与有效期基础：已实施

- 顶栏沿用紧凑卡片：头像字母、账号名、`角色 · APK 1`、有效期徽标。参考图只用于布局，账号、APK ID 和日期来自当前登录账号的服务端数据。
- APK ID 取 `accounts.apk_id`，一个账号一个固定编号，创建账号时在同一事务自动分配并写入 `apk_routes`；用户只读。不是「总台 AppID」，不是构建 UUID，也不随构建增加或更换。
- 增量迁移 `008_account_apk_id` 新增唯一账号编号及构建归属快照；`009_superadmin_apk_id_1` 将现有默认超管的规范编号固定为 `1`。旧 `10074` 等路由继续作为兼容别名保留，已有设备、历史构建和旧 APK 不改写；新账号从自身数值账号 ID 起查找未占用编号，重启不重新分配或恢复停用路由。
- SQLite 增量迁移 `007_account_validity` 添加 `accounts.valid_until`，UTC 毫秒截止时间，区间为 `now < valid_until`；原超管默认 `NULL`，表示长期有效，不改账号密码、归属或会话。
- `/api/auth/login` 和 `/api/auth/me` 的 `user` 新增 `apkId: string`、`validUntil: number | null`。原 `expiresAt` 仍是登录会话期限，不拿它显示续费到期日期。
- 日期按北京时间显示最后有效日。未来开通时选择「2026-10-11 到期」，服务端应保存 `2026-10-12T00:00:00+08:00` 对应的 UTC 毫秒值，10 月 11 日全天有效，到次日零点终止。正常日期用绿色，剩余 7 天以内用橙色，到期用红色；未知字段显示待确认，不当作长期有效。
- 服务端登录事务重新读取有效期，HTTP、面板 WS 消息与广播均检查有效期；签发的登录会话截止于 `min(当前时间 + 8 小时, valid_until)`，面板票据也不超过该会话。到期后旧会话不再访问设备、构建、下载等管理 API。扩展账号有效期不延长旧会话，重新登录取得新会话。
- 本次没有账号有效期修改入口，也没有放开总台/子账号登录。超管仍是唯一可登录角色；限期显示分支使用独立测试数据验收，不给当前超管填虚构日期。

## 后续方案：未实施

### 1. 账号层级

| 角色 | 建议范围 |
|---|---|
| 超管 | 全部工作室、全部设备、创建总台、归属调整及审计 |
| 总台 | 自己的工作室设备与配置；创建最多 5 个有效子账号；工作室内部下发设备 |
| 子账号 | 仅被分配给自己的设备及允许的功能 |

总台对应工作室租户，服务端内部使用 `studio_id` / `project_id` 做隔离。这些是内部归属主键，**不叫 AppID，也没有「总台 AppID」这一业务字段**。本轮没有提前加入租户表、创建账户路由或虚假的管理按钮。

后续实现时，所有查询、图片/导出、WS 订阅和广播必须统一校验角色与归属，不能只隐藏前端列表。5 个子账号的限额在数据库事务中检查，避免并发创建超额；父账号停用时一并撤销相关会话。

### 1.1 总台开通、到期与续费

1. **计费单位为总台 / 工作室**，超管负责开通和续期。创建总台时必须给出期限，不把空值默认为付费总台的长期许可；超管自身默认长期有效。先支持人工确认续费，不提前接支付平台。
2. 子账号默认继承总台期限；若另设子账号期限，有效截止时间取两者较早值。总台到期，旗下全部账号暂停管理权限；并发创建仍受每总台最多 5 个有效子账号约束。
3. 未到期续费从原截止时间续接，已到期续费从当前时间开始，即基准 `max(now, 原截止时间)`。首版建议明确按天购买（北京时间自然日截止）；若后续按自然月出售，单独确定月底规则，不把一个月默认为 30 天。
4. 续期操作在服务端事务内完成：校验操作者及租户范围、幂等业务单号、旧/新有效期、续期天数和审计。普通总台/员工不自行写入期限；客户端传入的期限不作为权限依据。支付接入后以验签回调和订单状态为准，不信任支付成功跳转页面。
5. 开通、停用、调整期限及续费统一重算总台与子账号权限，撤销受影响旧会话和 WS 订阅，重新登录才恢复。保留账号、APK 路由、设备归属和记录；到期不删除数据、不重新分配设备、不操作手机数据。设备侧应另行增加所属工作室有效期检查，禁止到期后新登记/新截图上传，并结束现有上传许可；该租户设备联动随总台实现，不冒充当前已具备。
6. 总台到期后登录提示联系平台续费；员工提示联系总台。即将到期提醒可以后续通过所属机器人发送，避免每次页面请求重复通知。机器人、专属域名和服务器均不绕过中央有效期校验。

以上开通/续费管理、订单、租户继承、设备联动和提醒仍为后续交付；当前只落实账号有效期基础字段、展示和登录/管理会话校验。

### 2. 只有 APK ID：区分构建、路由与凭证

- `APK ID`：创建账号时分配的固定业务编号；初始超管为 `1`。构建参数只用于选择接收账号，公开编号不具备身份验证能力。
- `构建 ID`：一次具体构建任务的标识，例如 `5412ce7f`，与 APK ID 分开。一次 APK 配置可有多个构建版本。
- 域名：负责连接到哪个服务入口；APK ID 负责查默认归属。域名不是用户账号，也不是权限凭证。
- 用户专属 APK 默认进入该用户的设备列表；总台 APK 先进入该总台待分配池；超管 APK 可进入平台待分配池，再经后台操作指定工作室与用户。
- 设备首次登记后，实际归属保存在服务端。后续下发更新服务端归属和审计，重新计算可见性/订阅并撤销旧权限；设备重新连接不得覆盖已生效的分配结果。
- APK ID 可公开，不能单独凭它信任数据或访问其他设备；每台设备仍需独立登记凭证，服务端校验设备与项目关系。

### 当前构建归属解析（已实现）

| 输入 | 构建结果 |
|---|---|
| 留空、空白或省略 apkId | 使用默认接收账号的固定编号，`default_empty` |
| 匹配本项目启用且未到期的账号固定编号 | 使用该账号及其编号，`explicit` |
| 格式正确但不存在、已停用、已到期、属于其他项目或仅为旧别名 | 使用默认接收账号，`default_unmatched`；不修改目标映射 |
| 超长、控制符、非编号字符 | 422 字段校验错误，不进入队列 |
| 默认接收账号/对应路由已停用 | 409，不生成无接收方的 APK |

当前只开放超管：默认接收账号是当前超管，域名只是连接地址，不用域名猜测租户。后续开放总台/子账号时，默认接收方必须由服务端认证后的所属工作室确定：子账号留空或填错归该总台；编号查询限本工作室，跨总台指定需独立的超管权限与审计。当前没有实施这套多租户账号接口。

- 解析在构建入队事务内完成；`apk_builds.apk_id` 是最终写入 APK 的实际编号，另存 `requested_apk_id / owner_account_id / owner_username / routing_reason` 供回执与构建记录展示。相同 requestId 重试读取原记录，不重新决定归属。
- 构建不创建账号/路由，也不覆盖已有设备归属。旧任务保留原始记录与 APK，不冒充已按新规则构建。
- `POST /api/apk-routes` 已移除；`GET` 保留供接入调试兼容旧 APK。临时登记码入口移至「账号设置 → 设备接入调试」。手机登记仍校验独立凭证和实际 APK ID，之后重连使用已固定的设备归属。

当前接入副本已经使用 APK ID 查后台默认归属，并保存设备实际 owner_account_id；目前只配置到超管。未实现总台/子账号、归属下发、旧设备恢复或多域名部署；原浏览器模板保持不变。

### 3. 专属域名、专属服务器与中央数据库

完整的数据流、首次上线、超管汇总、临时截图读取、节点断联及分期交付方案见 [多服务器设计](MULTI_SERVER_DESIGN.md)。该文为后续设计，当前域名字段仅写入 APK 连接配置，尚未绑定工作室或节点。

建议先用单 Node 服务与 SQLite 验证账号逻辑，再逐步拆分部署，而非现在启动微服务：

1. 一个工作室绑定一个经过验证的域名；服务端维护域名到工作室的映射，拒绝未知 Host。域名映射不替代账号权限校验。
2. 初期多个域名可指向同一服务与数据库；总台只访问自己的租户数据，超管保留全局视图。
3. 需要专属服务器时，中央服务保留账号、归属、构建配置和审计的权威数据。专属节点以工作室限定的服务凭证调用中央 API，断联时停止需要新权限确认的操作，不擅自扩大权限。
4. 不让多台服务器经共享磁盘直接读写同一 SQLite 文件；达到多节点/写入量需求后，迁移至集中 PostgreSQL/MySQL，或者继续由中央单服务独占 SQLite 并通过 API 访问。该数据库迁移尚未实现。

按「平台统一持有数据库、总台管理自己工作室数据」理解当前意图；若以后每个总台独立持库，需另定平台汇总和数据同步边界。

### 4. 总台机器人验证码

后续每个总台配置自己的机器人 Token（加密存储），用户经一次性短效绑定链接绑定 Telegram 私聊身份，不仅凭用户名绑定。登录流程建议：

1. 账号密码验证成功，生成短效登录挑战，此时还不签发账号 Token。
2. 为该挑战生成 6 位随机验证码，通过所属总台机器人发送给已绑定的私聊；显示用户、服务端获取的 IP 和 5 分钟有效期。
3. 只保存带服务端密钥的验证码校验值，绑定账号和挑战；一次使用、限次验证、限速发送。重发撤销旧验证码，成功或到期删除挑战。
4. 验证成功后再创建唯一会话并挤下旧登录；不让仅输入正确密码的人提前挤下正在使用的账号。
5. 机器人失联、未绑定、重绑定与丢失账号的人工处理流程需单独设计；错误和日志不记录验证码正文。平台超管的机器人归属也在这一阶段单独配置。

以上均为规划。当前账号密码可直接登录，机器人验证码尚未启用。
