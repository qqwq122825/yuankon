## 2. 当前最可信模型（原包重签 · 模型 A）

在 **82 极瘦包** 上，你的结果支持 **「原样 `classes.dex` + 未大剥 Manifest」→ 报毒**，且两条 **独立撤毒** 路径：

1. **Manifest 大剥**（83）：DEX 字节不变 → **正常**  
2. **DEX 末字节/头损坏**（84、85）：Manifest 仍全 → **正常**

因此更不像「整包 MD5 一条命」，而像：

- **本地规则 A**：`classes.dex` **精确指纹**（或头+体校验）  
- **本地规则 B**：Manifest **权限/queries/a11y 相关 + 组件面**（大剥后 83 不满足）  
- **82 报毒** ≈ **A 与 B 同时满足**（或引擎对极瘦包用 **AND**）

**87 仍报毒**：资源/arsc/assets/so 仍在 → **其它特征线**（如 arsc、整包）仍命中，单靠 Manifest 大剥不够。

**89 仍报毒**：包名改为 `com.boundary.install.probe`，**DEX 仍是原 bytecode** → 包名 **不是**极瘦形态下的主键。

**77–79 仍报毒**：与 87 一致，**删掉 assets 或 lib  alone 不够**。

## 4. 88 vs 83 为何可能不一致

- **83**：先极瘦 → 再 Manifest 大剥 → **正常**  
- **88**：先 Manifest 大剥 → 再极瘦 → 你测 **报毒**

理论上最终 ZIP 应接近；若仍不同，可能原因：Manifest 二进制两次编辑路径不同、或扫描还看 **签名/APK 外层 hash**。可后续用 `apksigner verify` + 对比 `AndroidManifest.xml` 字节排查；引擎侧应对 **83/84 与 82** 对齐策略，避免「先删文件再剥 Manifest 就放行」的 **顺序漏洞**。

## 5. 与加壳线（56 / 59）并存

| 线 | 条件 | 典型结果 |
|----|------|----------|
| **B 加壳瘦包** | 56 无 arsc | 正常 |
| **B** | 59/75/76 有 arsc | 报毒 |
| **A 原包极瘦** | 82 原 DEX + 全 Manifest | 报毒 |
| **A** | 83/84/90 | 正常 |

产品上要 **两条链都扫**：B 禁止「无 arsc 默认安全」；A 禁止「Manifest 大剥 + 未改 DEX 仍应报却放行」或反之「仅 DEX hash 黑名单但改 1 字节就过」。
