## 3. arsc 篡改三件套怎么读

### 3.1 与 DEX 线对比（同一台引擎上的重要差异）

| 资源 | 轻微篡改 | 历史/suite 现象 | 解读 |
|------|----------|-----------------|------|
| **classes.dex** | 末字节翻转 | **#90 / 2 正常** | 存在 **精确 DEX 字节/哈希** 类规则，改 1 字节可脱钩 |
| **resources.arsc** | 首/末字节翻转 | **10、11 仍报** | 规则更像 **多段特征 / 模糊匹配 / 解析后语义**（包名串、应用名、图标 id 等），**1 字节不够** |

因此：**不能**假设「arsc 和 dex 一样改 1 字节就能过扫描」。

### 3.2 为何 10、11 仍报

合理假设（需后续探针 narrowing，见 §5）：

1. **特征不在单字节**：CRC/哈希块、多处子串、或解压/解析 arsc 后的 **字符串/资源 entry** 仍匹配毒库。  
2. **与包名组合**：`org.helper.scannertask` + 原 arsc 内容联合 scoring（**12 未测信誉**）。  
3. **云库/多段 hash**：改 1 字节未跳出阈值。

### 3.3 为何 12「解析有问题」

- **构造**：在 **6** 上对 `resources.arsc` 做 **尾部 4096 字节抹零**（`zero_tail:4096`）。  
- **预期行为**：Android 资源编译表 **尾部损坏** → PackageManager / aapt2 / 扫描器 **解析 arsc 失败** → 用户看到 **解析失败** 而非明确的「报毒/正常」。  
- **与 #74**：历史矩阵 **arsc 全 0** 也为 **解析失败** → **12 属于损坏探针**，不是「绕过报毒」的交付路径。  
- **引擎建议**：解析失败应 **拒绝安装**，且 **不得** 弱于「完整 arsc 报毒」的安全策略（避免损坏包变免扫通道）。

## 7. 产品 / 引擎策略（草案，供安全中心）

1. **resources.arsc**：对已知样本 **整表或解析后特征** 命中；**单字节改动仍命中**（10/11）。  
2. **与 dex 策略分离**：dex 末字节翻转 **不能** 类推 arsc。  
3. **损坏 arsc**：**解析失败 → 拒绝**（12），且不弱于报毒路径。  
4. **无 arsc 的极瘦/56 形态**：**不能默认安全**（仍有 payload/so/dex 等其它线，见 3/91）。  
5. **合规构建**：新 applicationId + 新资源编译 → **新 arsc**，禁止复制 5412ce7f 的 arsc 块。
